# Architecture Decision Record: Core Technology Stack

**Title:** Core Technology Stack for SaveSync
**Date:** 2026-10-20
**Status:** Accepted

## Context

SaveSync is a data-integrity-sensitive desktop application that must protect user game saves from accidental loss or corruption. The application must be cross-platform (Windows 11, CachyOS, Bazzite), desktop-native, durable, offline-capable, and capable of versioned synchronization between local storage and a Google Drive backend.

Initial proposed stack:
- Tauri 2 for the desktop shell.
- Rust for the core engine and filesystem operations.
- React + TypeScript for the UI.
- SQLite for local metadata and job state.
- Ludusavi CLI for save discovery and backup/restore integration.
- Google Drive API v3 for remote storage.
- SHA-256 for integrity verification.

The goal is to produce a coherent implementation domain separated into clear components.

## Decision

We adopt the following core technology stack:

| Layer | Technology | Version | Justification |
|-------|-----------|---------|---------------|
| Desktop Shell | [Tauri 2](https://tauri.app/release/) | v2.12.3 (stable) | Matures for large-scale apps, first-class Webview2/WKWebView integration, better security story. |
| Core Language | Rust | 1.99+ | We already have a Rust-based environment (Arch Linux), mature tooling for filesystem, hashing, concurrency, and SQLite. |
| UI | React + TypeScript | Latest stable | RedwoodJS/T3 ecosystem expectations; broad tooling and debugging support; dark-first design feasible via Tailwind + shadcn/ui. |
| Local Metadata | SQLite | Latest stable via `rusqlite` | Mature, file based, supports migrations, crash recovery via WAL, transactional consistency. |
| Save Discovery & Backup | Ludusavi CLI | v0.x.x (ship with app) | We control the binary; using `--api` JSON mode for safe, predictable execution (no prompt injection, handles stdout/stderr distinctly). |
| Remote Storage | Google Drive API v3 | REST v3 | Documented, supports file-based objects, list/get with `/?alt=media`, resumable uploads with `uploadType=resumable`, proven OAuth flow. |
| Content Hashing | SHA-256 | `sha2` crate | Standard, fast, part of Rust stdlib without unsafe. |
| Build System | Cargo and Tauri CLI v2.12.2 | Latest | Integrated Rust tooling; `tauri-build` and `tauri-bundler` packaged with Tauri. |

### Google Drive Integration Details

- **Scope:** `https://www.googleapis.com/auth/drive.file`. Per the official docs, this is a non-sensitive scope that grants per-file access launched by the app itself—adequate for user-selected save snapshots.
- **API Version:** REST v3 (same as documentation anchors).
- **Session:** No use of the Gomez or REST v2; keep stable v3.
- **Paths:**
  - List existing app objects: `GET /drive/v3/files?q=appProperties hasKey "secondarySystemId" and parents='[YOUR_APP_FOLDER_ID]'`
  - Insert new object: `POST /upload/drive/v3/files?uploadType=multipart` with metadata as `name`, `mimeType`, and file body (blob or multipart/related). Use `multipart` to upload name and content atomically.
  - Download blob: `GET /drive/v3/files/{fileId}?alt=media` to stream to disk or a temporary location.
  - Resumable upload for large snapshots: GET /upload/drive/v3/files with `uploadType=resumable`, then PUT session URL with `Content-Range`.
- **Repository:** Use an app-only folder (Drive notion) for permanence; path logic is relative to that folder.
- **Retry & Backoff:** Apply bounded exponential backoff with jitter on 5xx, 403 rate limits, and transient errors (network and reads). Retention: no storage quota attribute from API; use SQLite to track size and retention policy.

### Ludusavi Integration Details

- **Interaction Mode:** We invoke ludusavi from Rust using `std::process::Command`. We check exit code and stdout carefully.
- **Mode:** JSON API via `--api` flag (`ludusavi backup --force --api`). Output goes to stdout; stderr is treated as non-API warnings/errors.
- **Validation:** We enforce that output `kind` is `"backup"`, `games` is present, and we reject commands with nonzero exit codes or missing outputs.
- **Storage:** We respect the "download" directory configured by users; we do not forcibly share or modify their personal Ludusavi settings.
- **Fallback:** If manifest-backed discovery fails, we support user-configured custom save directories (see Platform Adapters component).

*Note: All other game platforms (emulators, custom save profiles) must be supported via the generic Platform Adapter interface, not via external tooling.*

## Alternatives Considered

| Alternative | Pros | Cons | Outcome |
|-------------|------|------|---------|
| Electron instead of Tauri | Mature ecosystem, large third-party modules, cross-compiled bun/unpacked bundles trivial; low friction. | Separate runtime process (multiple nodes), less control, proven memory usage issues, larger bundles. | Rejected in favor of Tauri’s single-process Rust+WFE model, better security and smaller binaries, primary ecosystem aligns with our stack. |
| Drogon/Ergo for backend, React for UI | Declarative JS, dense code, efficient reactive UI. | Less emphasis on filesystem from single runtime; heavier dependency overhead. | Retained Rust + API approach for core; UI moves to React per stack. |
| Local filesystem only, no cloud | Simpler architecture, no provider dependencies. | Forces user to manually aggregate saves; apt for a GDrive-native tool. | Keeping GDrive as optional via Provider abstraction; local core is instructorally complete. |
| REST v2 Mirror | Long-lived status stable. | Migration path; functionality present; reason to remain on v3 with v2 support available. | Opting for v3 to align with current docs and features. |
| Content-addressed storage (CAS) beyond file-level snapshots | Guaranteed reference; strong redundancy; BFG or `gix` support. | Project scope limited to first inch; adds design complexity (blobs, dedup). | Will implement simple file-based snapshots with SHA-256 first, primarily to establish unambiguous recoverability. |
| Fully managed cloud storage (pCloud, Dropbox) | Simpler credentials, familiar UI patterns. | Integration overhead with larger vendors, different scope policies, potential for conflicting semantics. | Focused on Drive as data lever per user’s ecosystem; orthogonal providers can be added later. |

## Consequences

### Security and Privacy
- Using `drive.file` ensures we only touch user-selected files.
- All cloud metadata (file IDs, content hashes) is stored locally, not in user-provided data.
- Ludusavi is invoked with full CLI arguments; we do not parse manifests from user-provided files directly.

### Development Experience
- We must maintain up-to-date Rust targets; we already have [Rust 1.99](https://raw.githubusercontent.com/sturkmen711/ludusavi/main/README.md) and [Cargo 1.99.1](https://raw.githubusercontent.com/sturkmen711/ludusavi/main/README.md) suitable across Windows, Linux, and macOS.
- Tauri requires system provisioning: Windows needs WebView2; Linux needs webkit2gtk (webview2gtk-4.1) or wpebackend-fdo and Adwaita theming; macOS needs Xcode + Xquartz + entitlements. We rely on packaging group for this.

### Performance and Efficiency
- Tauri 2 bundling shrinks footprint vs Electron; binary at code size ~5–10 MB depending on feature set (static Rust linking preferred).
- Rust ensures deterministic performance, no garbage collection pauses.
- Keep snapshots below 5 MB for simple upload factor; use resumable uploads otherwise.

### Portability
- We target distribution bundles for Windows (.msi/.zip), Linux (.AppImage/.deb), macOS (.dmg/.pkg) using `tauri-bundler`.
- Save paths are normalized through Rust `std::path` and scrubbed of symlinks/paths traversal components prior to enrolling.

### Operations & Maintenance
- Upstream versions update quarterly; we will pin ranges in `Cargo.toml` and `package.json`.
- User-provided Ludusavi updates via Flathub/flatpak are compatible; we verify executable version compatibility in health checks.

### Testing
- Integration tests will use a mock GDrive HTTP server; real OAuth is unnecessary.
- We'll mock Ludusavi stdout for deterministic invocation; link locally for real cases if possible.

## Dependencies and Replacements

### Planned Dependencies (first vertical slice)
- `libsqlite3`: SQLite3 library via `rusqlite` (nice for compatibility).
- `sha2`: Provides `sha2` crate for `Sha256`.
- `serde` and `serde_json`: For both Rust and TypeScript interfaces.
- `chrono`: Timezone-agnostic timestamp handling.

### Potential Future Dependencies
- `reqwest`: For HTTP client if we skip Google HTTP Client Libraries; good for streaming and retries.
- `tower` / `hyper`: For request retry and jitter (bounded cancellation).
- Hibernate for UI: React Router for SPA navigation, TanStack Query for cache; not permanent.

**Open Questions:**
1. Do we adopt a strict version range (`>=1.70 <2.0`) or latest stable? We lean on Pin and caution for rapid updates.
2. Should we use `tokio` for async Core? Decided: yes, but ensure all database use is sync; avoid async DB to keep SQLite transactional semantics clear.
3. API source of truth for PC game save paths: Should we subscribe to `ludusavi-manifest` API for real-time updates, or ship an embedded manifest? Decided: Provide an embedded JOSN manifest released with Desktop app; refreshable via Health Check.

**Rationale:** All decisions prioritize debuggability, platform portability, and local-first backup safety.
